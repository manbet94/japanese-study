# /release — 새 버전 배포

사용자는 처음 개발을 해 보는 사람이다. 모든 안내는 쉬운 한국어로, 단계마다 무엇을 했는지 짧게 말한다.
사용자가 `/release`를 직접 입력한 것 자체가 "이번 변경을 배포해 줘"라는 요청이다. 그래도 커밋·푸시 직전에 한 번만 확인을 받는다.

## 이 앱의 업데이트 구조 (먼저 알고 시작)

- 서비스 워커는 `vite-plugin-pwa`의 `generateSW`가 빌드할 때마다 새로 만든다. 파일 내용이 바뀌면 파일 이름의 해시와 precache 목록이 자동으로 바뀌므로 **캐시 버전 번호를 손으로 올릴 필요가 없다.** `CACHE_NAME` 같은 값을 새로 만들지 말 것.
- 폰에서 새 버전을 받는 것은 `src/main.tsx`의 `registerSW({ immediate: true })`와, 앱으로 돌아올 때(`visibilitychange`)의 업데이트 확인이 맡는다. 이 코드를 지우거나 바꾸지 말 것.
- 그래서 "폰에서 업데이트가 안 보여요"를 막는 핵심은 ① 빌드가 성공해서 새 `sw.js`가 나가고 ② 배포된 사이트에 새 버전이 실제로 떴는지 **확인하는 것**이다.

## 1. 출발 상태 확인

1. `git status -sb`와 `git fetch -q origin`을 실행한다.
   - main 브랜치가 아니면 멈추고 알린다.
   - origin/main보다 뒤처져 있으면(behind) 멈추고 알린다. 사용자 허락 없이 pull·merge 하지 않는다.
   - 커밋되지 않은 변경도 없고 origin보다 앞선 커밋도 없으면 "올릴 변경이 없어요"라고 알리고 끝낸다.
2. 바뀐 파일 목록을 보여 준다. `.env`처럼 비밀이 들어 있을 만한 파일이 있으면 커밋에서 빼고 알린다.

## 2. 새 버전 번호 정하기

1. 지금 버전은 `src/pages/Home.tsx`의 `목표: SJPT 레벨 5 · vX.Y.Z` 에서 읽는다.
2. `$ARGUMENTS`에 버전이 있으면 그것을 쓴다(앞의 `v`는 있어도 없어도 됨). 없으면 AskUserQuestion으로 묻는다.
   - 추천(첫 번째): 끝자리 +1 (작은 기능·수정). 예: 0.2.1 → 0.2.2
   - 둘째 자리 +1 (큰 기능 묶음). 예: 0.2.1 → 0.3.0
3. 새 버전이 지금 버전보다 크지 않으면 멈추고 다시 묻는다.

## 3. 버전 표시 올리기

아래 세 곳을 Edit 도구로 고친다. PowerShell `Set-Content`로 고치지 않는다(한글이 깨짐).

- `src/pages/Home.tsx`: `SJPT 레벨 5 · vX.Y.Z`
- `src/pages/SettingsPage.tsx`: `日本語 매일 20분 · vX.Y.Z`
- `package.json`: `"version": "X.Y.Z"` (`package-lock.json`의 맨 위 두 `version`도 같이 맞춘다)

`Home.tsx`의 "다음 업데이트" 목록에 이번 버전 줄이 있으면 지우고, 지웠다고 알린다.

## 4. 검사 (하나라도 실패하면 멈춤)

순서대로 실행한다. 실패하면 커밋하지 말고, 무엇이 왜 실패했는지 쉬운 말로 설명한 뒤 고칠지 묻는다.

1. `npm test`
2. `npm run lint` — 경고는 괜찮지만 error가 있으면 실패로 본다.
3. `npm run build` — 출력에 `PWA`와 `dist/sw.js`가 있는지 확인한다(서비스 워커가 새로 만들어졌다는 뜻).

## 5. 확인받고 커밋·푸시

1. AskUserQuestion으로 한 번만 확인한다. 질문에 새 버전, 바뀐 파일 수, 커밋 메시지 첫 줄을 넣는다. 선택지: "배포해 주세요"(추천) / "아직 안 할래요".
   - 이번 변경에서 `src/db/db.ts`에 새 `db.version(n)`이 생겼다면(폰 저장소 구조 변경), 질문에 "배포 전에 폰에서 **설정 → 백업 파일 저장**을 먼저 해 두세요"를 함께 적는다. 폰은 앱을 여는 순간 새 버전으로 바뀌므로 백업은 배포 전에 해야 한다.
2. 커밋 메시지는 이 저장소의 기존 방식을 따른다: 첫 줄 `vX.Y.Z: <바뀐 내용 한 줄 요약>`, 빈 줄, `- ` 로 시작하는 변경 목록(한국어). 세션이 정한 커밋 서명(Co-Authored-By) 규칙을 따른다.
3. 파일은 이름을 하나씩 지정해서 `git add` 한다(`git add -A` 쓰지 않음).
4. git 사용자 설정(이름·이메일)은 절대 바꾸지 않는다. 공개 커밋에 개인 이메일이 나가지 않도록 저장소에 noreply 주소가 설정되어 있다.
5. `git push origin main`. 강제 푸시(`--force`)는 하지 않는다.

## 6. 배포 확인 (꼭 끝까지)

푸시하면 GitHub Actions가 빌드해서 https://manbet94.github.io/japanese-study/ 에 올린다. 보통 1~3분 걸린다.
`gh`는 로그인되어 있지 않을 수 있으니 사이트를 직접 확인한다. Bash로 10초마다 최대 7분 동안 확인한다:

```bash
U=https://manbet94.github.io/japanese-study/; M='레벨 5 · vX.Y.Z'
for i in $(seq 1 42); do
  js=$(curl -s "$U?t=$RANDOM" | grep -o 'assets/index-[^"]*\.js' | head -1)
  if [ -n "$js" ] && curl -s "$U$js" | grep -q "$M"; then echo "LIVE $js"; exit 0; fi
  sleep 10
done; echo "NOT LIVE"
```

- 확인할 글자는 반드시 `레벨 5 · vX.Y.Z` 처럼 **버전 표시 문장 전체**로 한다. 버전 번호만 찾으면 "다음 업데이트" 목록에 같은 번호가 미리 적혀 있을 때 옛 버전을 새 버전으로 착각한다.
- 7분이 지나도 안 뜨면 실패라고 솔직히 알리고, GitHub 저장소의 Actions 탭(https://github.com/manbet94/japanese-study/actions)에서 빨간 X가 있는지 봐 달라고 안내한다.

## 7. 마무리 안내

쉬운 한국어로 짧게 알린다:

- 새 버전 번호, 커밋 번호(7자리), 배포된 사이트에서 확인했는지
- 폰에서 받는 법: 앱을 껐다 켜거나 다른 앱에 갔다 돌아오기 → 홈 위에 새 버전이 보이면 끝. 안 보이면 **설정 → 🔄 앱 새로고침**.
- 학습 기록은 폰에 그대로 남는다는 점
